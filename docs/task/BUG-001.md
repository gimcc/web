# BUG-001 重构消息处理体系（参考 Cinny）

- **priority**: P0
- **status**: investigation
- **owner**: —
- **created**: 2026-03-20

## 问题描述

消息不会自动出现在时间线中，疑似状态一致性问题。需要参考 Cinny 的实现重构消息处理体系。

## 根因分析

### 已确认的 Bug

1. **加密消息无法实时显示** — `onTimeline` 收到 `m.room.encrypted` 类型事件时，`processTimelineEvent` 只检查 `m.room.message`，加密事件被静默忽略，直到下次 `loadInitialTimeline` 才会出现。
2. **分页事件被当做实时事件处理** — 旧代码没有检查 `toStartOfTimeline`，SDK 的 scrollback 事件也会进入 `processTimelineEvent`，导致重复或乱序。
3. **自己消息的 echo 去重逻辑有缺陷** — 旧代码 `hasPending` 为 true 时直接 return，不调用 `confirmMessage`，导致消息卡在 `sending` 状态。
4. **`loadInitialTimeline` 与实时同步竞争** — `setTimeline` 会替换整个 timeline，sync 期间到达的消息可能被覆盖。

### 架构层面的根因

我们的架构维护了一个独立的 Zustand store 作为消息状态，需要通过 sync-bridge 手动桥接 SDK 事件到 store。这个桥接层容易产生以下问题：

- **双源状态不一致** — SDK timeline 和 store timeline 是两份独立数据，需要手动保持同步
- **事件处理遗漏** — 任何新的事件类型或关系类型都需要在 bridge 中显式处理
- **时序竞争** — API 响应、sync echo、timeline reload 之间存在竞态条件

### Cinny 的做法（对比）

Cinny **直接使用 SDK 的 EventTimeline 对象**作为数据源：
- 不维护独立消息 store，渲染时直接读取 `timeline.getEvents()`
- SDK 内部自动处理编辑、reaction、redaction 等关系
- 通过 `setTimeline({ ...ct })` 触发 React 重渲染，数据始终来自 SDK
- 使用 `data.liveEvent` 精确判断实时事件

## 完整缺陷清单（对比 Cinny 分析）

> 来源: `docs/analysis-cinny-vs-gim.md`

### CRITICAL

| # | 缺陷 | 描述 | 工作量 |
|---|------|------|--------|
| C1 | 无双向 timeline 导航 | 只有扁平 `TimelineMessage[]`，无法跳转到任意事件或从某事件双向分页。无法实现"点击回复跳转"、通知深链接、`RoomEvent.TimelineRefresh` 处理 | 大 |
| C2 | `loadRoomHistory` 全量替换 timeline | 调用 `setTimeline()` 覆盖整个数组，实时同步到的消息和 reaction 可能丢失。`mergeStoreReactions()` 是脆弱的 workaround | 中 |

### HIGH

| # | 缺陷 | 描述 | 工作量 |
|---|------|------|--------|
| H1 | 未监听 `RoomEvent.TimelineRefresh` | SDK 重置 timeline 时（sync gap / limited timeline），UI 继续显示过期数据 | 小 |
| H2 | 缺少事件类型渲染 | 只处理 `m.room.message`。缺少: `m.sticker`、`m.room.member`（加入/退出/邀请/封禁）、state event（房间名/主题变更等） | 中 |
| H3 | 无消息折叠/分组 | 同一发送者 2 分钟内的连续消息应折叠头像和用户名（Cinny 实现），目前每条都完整显示 | 中 |
| H4 | 无日期分割线 / 未读分割线 | 无法区分不同天的消息，无 "New Messages" 分界标记 | 小 |

### MEDIUM

| # | 缺陷 | 描述 | 工作量 |
|---|------|------|--------|
| M1 | 向上加载历史后滚动位置跳动 | `setTimeline()` 全量替换数组导致所有 index 变化，`@tanstack/react-virtual` 无锚点稳定机制 | 中 |
| M2 | Store 订阅低效 | `useMessagesStore(s => s.timelines)` 订阅整个 Map，任何房间更新都触发当前房间重渲染。应改为 `s => s.timelines.get(roomId)` | 小 |
| M3 | 乐观消息匹配脆弱 | 快速连发多条时，`timeline.find(m => m.eventId.startsWith('~') && m.status === 'sending')` 匹配到的是第一条 pending 消息，若服务端重排顺序会匹配错 | 小 |
| M4 | 加密消息处理不完整 | 解密后只处理 `m.room.message`，加密的 sticker、member event 等被丢弃 | 小 |

### LOW

| # | 缺陷 | 描述 | 工作量 |
|---|------|------|--------|
| L1 | 已读回执切房间后重复发送 | `lastSentReceiptRef` 不跨房间持久化，重进房间可能重发已发过的回执 | 小 |
| L2 | 无 "Jump to Latest" 复位 | 滚动到深处历史后，只有滚动按钮，没有重新加载 live timeline 的机制 | 小 |

## 已确认修复项

- [x] Bug 1: 加密消息无法实时显示（已在当前分支修复：监听 `MatrixEventEvent.Decrypted`）
- [x] Bug 2: 分页事件被当做实时事件处理（已在当前分支修复：检查 `toStartOfTimeline`）
- [x] Bug 3: 自己消息的 echo 去重逻辑缺陷（已在当前分支修复：`confirmMessage` 逻辑重写）
- [ ] Bug 4: `loadInitialTimeline` 与实时同步竞争（部分缓解：合并后排序，但根因未解决）

## 重构方向建议

短期（修补现有架构）:
1. 修复 C2 — `loadRoomHistory` 改用 `prependMessages()` 而非 `setTimeline()`
2. 修复 H1 — 添加 `RoomEvent.TimelineRefresh` 监听
3. 修复 M2 — 优化 store selector
4. 修复 H3/H4 — 在 `MessageTimeline` 中实现分组和分割线

中期（架构演进）:
- 考虑 Cinny 模式：直接读取 SDK `EventTimeline` 对象，移除独立 store
- 或保留 store 但改为使用 SDK timeline 作为 source of truth，store 仅做缓存层
